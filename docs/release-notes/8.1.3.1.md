## What's changed

Binding-pin update that moves Android to FFmpeg `8.1.3` and fixes a freeze on Android. iOS and macOS stay on FFmpeg `8.1.2`. The cross-platform API is unchanged from `8.1.2.3`.

| Platform | FFmpeg | Binding |
| --- | --- | --- |
| Android | `8.1.3` | `8.1.2.5` → `8.1.3.1` |
| iOS | `8.1.2` | `8.1.2.3` |
| macOS | `8.1.2` | `8.1.2.2` |

```
FFmpegKit.Net.<Variant>.Maui        MAUI wiring: UseFFmpegKit()/AddFFmpegKit() + FilePicker/SAF helper
  └─ FFmpegKit.Net.<Variant>        the cross-platform API   (Android, iOS, macOS)
       ├─ FFmpegKit.Net.<Variant>.Android   8.1.2.5 → 8.1.3.1   FFmpeg 8.1.3
       ├─ FFmpegKit.Net.<Variant>.iOS       8.1.2.3             FFmpeg 8.1.2
       └─ FFmpegKit.Net.<Variant>.Mac       8.1.2.2             FFmpeg 8.1.2
```

The version number of this package now names the newest FFmpeg among the platforms, not an FFmpeg that all of them share. If you depend on a specific FFmpeg, check the table above for your platform, or run `-version` through `FFmpegKit.ExecuteAsync` to see what your app actually carries.

### Fixed on Android: the app freezes after an FFmpeg command

Through `8.1.2.3`, an Android app on the default Mono runtime could freeze for good at the first garbage collection after it ran an FFmpeg command, usually ending in Android's "isn't responding" dialog. How soon that happened depended on how much the app allocated, so a small test app could run for a long time without showing it.

Mono on Android restarts the threads it stopped for a collection with `SIGXCPU`. FFmpeg installs its own `SIGXCPU` handler when a command runs, so the restart never reached Mono and those threads stayed suspended.

The Android binding `8.1.3.1` fixes it, and the fix reaches your app through this package: every Android call here goes through the binding types that apply it. Nothing in your code changes; upgrading is a version bump.

### New on Android with FFmpeg `8.1.3`

These come from the Android binding, so they do not apply to iOS or macOS:

- **Security:** upstream reports that FFmpeg `n8.1.3` closes CVE-2026-64830 (VobSub demuxer) and CVE-2026-64835 (ADX decoder), both reachable in this build.
- **`drawtext` is back** in `Full`, `FullGpl` and `Video`.
- **A `-filter_complex` parse error no longer kills the process**, according to upstream.
- **`Min` and `Https` now carry `libc++_shared.so`**, which adds about 1.8 MB per ABI before compression.

The [Android `8.1.3.1` release note](https://github.com/sbokatuk/FFmpegKit.Android/blob/main/docs/release-notes/8.1.3.1.md) has the details.

iOS (`8.1.2.3`) and macOS (`8.1.2.2`) pins are unchanged.

### Reminder: the API this package adds

Unchanged since `8.1.2.1` — one `FFmpegKit`/`FFprobeKit`/`FFmpegKitConfig` surface across Android, iOS and macOS, awaitable with `CancellationToken`, `IProgress<FFmpegProgress>` reporting, typed `MediaInfo` parsed invariant-culture everywhere, the failed command's console `Output` on the result, `EnsureSuccess()` for exception-preferring code, and an injectable `IFFmpegKit` registered by `UseFFmpegKit()` / `AddFFmpegKit()`.

### What was tested

Against the packed packages:

- All 45 unit tests and all 9 package tests.
- The device checks through this package: `Full` and `Video` on Android (`net10.0-android36.0`), `Full` on the iOS simulator (`net10.0-ios26.0` and `net9.0-ios18.0`) and on macOS (`net10.0-macos26.0`). FFmpeg reports `n8.1.3` on Android and `n8.1.2` on iOS and macOS.
- The sample on an API 35 Android emulator (`net10.0-android36.0` and `net9.0-android35.0`) and on an iOS 26 simulator (`net9.0-ios18.0`): media probe, resize, grayscale and audio extraction. On `net10.0-ios26.0`: media probe and resize.
- The freeze: with a garbage collection forced every second, the Android sample ran nine conversions without freezing. The same test on `8.1.2.3` froze on its first conversion.
